## Capture lineage and identity

Both handlers verify the HMAC-SHA256 signature over exact request bytes before parsing JSON or making RPC calls. Official uses endpoint `line_official_webhook_test`, source ref `LINE_OA:MEYOU_CONNECT_OFFICIAL`, and event IDs beginning `LINE:OFFICIAL:`. Data Bot uses `line_group_bot_webhook_test`, source ref `LINE_OA:MYC_DATA_BOT`, and `LINE:DATA_BOT:`. The handlers call `line_capture_ingest`, which calls `ops.secure_ingest_material_event`; that calls `ops.ingest_material_event` and eventually `ops.register_event`. Successful capture calls `ops.complete_raw_capture_event`, which calls `ops.route_line_raw_event_v1`.

The deployed `register_event` definition returns an existing row on source/event ID or idempotency-key matches without comparing the new content. Existing capture SQL independently allowlisted endpoint and account sets, rather than pairing them. Its raw-map key contained the full scoped event ID. The SQL review candidate preserves that key format, pairs endpoint to account, validates the account prefix, and stores a SHA-256 fingerprint of a canonical immutable envelope. It omits provider token fields and redelivery flags while preserving array order and treating an absent delivery context like one containing only a redelivery flag. Exact retries retain the same identity; changed payload under that scoped key returns `LINE_EVENT_ID_PAYLOAD_CONFLICT` before ID allocation or secure ingestion. A legacy map row with complete, verifiable raw/event lineage can be fingerprinted in memory and compared without changing historical data. Missing or unprovable lineage returns `LINE_EXISTING_FINGERPRINT_REQUIRES_REVIEW`.

## Handler safeguards

- The body reader stops at 2 MiB, matching the enabled TEST ingress policies; oversized requests receive HTTP 413 before signature parsing or any RPC. After signature validation, batches above 100 events receive HTTP 413 before writes. Each captured event continues to pass the full request byte count to the request-level ingress guard.
- The entire sanitized event is retained in the sensitive raw envelope, but token-like fields are removed case-insensitively. Stable provider identity uses `webhookEventId` or `message.id`. Missing stable IDs fail with HTTP 400 by default. An explicit `LINE_ALLOW_CANONICAL_FALLBACK_EVENT_ID=true` opt-in uses recursively sorted object keys, preserves array order, and omits token fields to derive a deterministic fallback.
- Attachments stream into bounded memory up to 10 MiB per file and 20 MiB per webhook batch. The stream is cancelled as soon as a limit is crossed; a batch that reaches its budget defers later files so a replay can progress them. Transient fetch, upload, token, and registry failures record `SOURCE_NOT_MIRRORED` and cause HTTP 503 after every valid event in the batch has been captured and processed. This requests provider redelivery only when LINE redelivery is enabled; it is not a durable media worker. If redelivery is unavailable, operators must use the bounded manual recovery path: inspect the safe status/reason, then explicitly replay the same source event after correcting the prerequisite. Oversized files (`ATTACHMENT_TOO_LARGE`) and permanent LINE content-not-found (`LINE_CONTENT_NOT_FOUND`) are held with actionable reasons and are not retried automatically. The cap is not enforced by the bucket itself.
- An explicit `REPLAY_DETECTED` decision skips enrichment. SQL marks `media_recovery_required` only when a prior attachment lacks a completed mirrored registry row with checksum; in that case the handler retries media recovery against the same raw ID. A completed mirror replay performs no media work. Fallback canonicalization is disabled by default; when explicitly enabled it strips redelivery flags and delivery context consistently.

That establishes downstream event/effect routing; the mocked tests do not prove any business-master mutation, candidate persistence, or production Facebook behavior. The deployed candidate tick uses `ops.apply_failure_transition` with the existing `candidate_intake` worker, retries only when due, clears route-error markers after a successful route, and stops processing held or terminal events. It adds no scheduler job or worker key.
